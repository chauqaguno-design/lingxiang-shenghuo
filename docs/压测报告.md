# 邻享生活实测报告

测试日期：2026-10-21。以下均为实际执行结果，原始样本与参数位于 [loadtest/evidence](../loadtest/evidence)。

## 环境与口径

- Windows 11，AMD Ryzen 9 8945HX（16 核 / 32 线程），约 32 GB 内存。
- Java Corretto 8，应用堆 128～512 MB；JMeter 5.6.3，堆 256～512 MB。
- Docker Desktop：MySQL 8.0.43、Redis 7.2.10、RocketMQ 4.9.6。
- 应用、JMeter、中间件同机；其他已有服务也在运行。
- 6 家商户、6 张券，查询接口返回 1 张券。这是小数据量、单轮、本机短时对照，不能代表生产容量。
- JMeter 使用 CLI，保留原始失败状态；库存不足和限购属于业务拒绝，HTTP 429 单独统计。
- 查询配置 20 线程，2 秒升压，每线程 100 次。各组先以 20 × 10 预热。线程很快结束，实测同时活跃线程未达到 20。

## 查询对照

接口：GET /voucher/list/1。三个模式查询相同数据，各 2,000 次请求。

| 模式 | 平均耗时 | P95 | P99 | 原始失败率 | 实际采样窗口 | 峰值活跃线程 |
|---|---:|---:|---:|---:|---:|---:|
| 直接 MySQL | 2.23 ms | 4 ms | 6 ms | 0% | 1.984 s | 12 |
| Redis | 1.78 ms | 3 ms | 5 ms | 0% | 1.968 s | 11 |
| Caffeine + Redis | 0.75 ms | 2 ms | 4 ms | 0% | 1.880 s | 10 |

本次样本中两级缓存延迟较低，但查询数据很小、运行时间很短、升压过程占比高，不能据此声称系统吞吐提升数倍，也没有测出容量上限。JTL 的观测吞吐保留在 summary.json 中，不作为简历中的生产 QPS。

三个模式只改变 app.voucher-cache.mode。缓存命中路径无需访问数据库，但这次未用数据库监控统计实际 SQL 降幅，因此不填写“数据库负载下降多少”。

## 50 用户抢 30 张券

活动 101，初始库存 30；50 个合成用户，每个发起 1 次请求。登录与抢券分开统计，订单支付期限临时设为 600 秒，验收快照在超时前取得。

| 项目 | 实测 |
|---|---:|
| 抢券请求 | 50 |
| 受理 | 30 |
| 库存不足拒绝 | 20 |
| HTTP / 断言失败 | 0 |
| 抢券平均 / P95 / P99 | 111.58 / 181 / 189 ms |
| 最终数据库订单 | 30 |
| 不同购买用户 | 30 |
| 重复用户订单组 | 0 |
| MySQL / Redis 剩余库存 | 0 / 0 |
| 受理订单号集合与落库集合一致 | 是 |

这里“业务拒绝率”为 40%，不是 100% 下单成功。入口返回成功只代表受理；最终 30 单是等待 MQ 消费后另外查询数据库得到的结果。

## 重复抢券与限流

活动 102；同一用户在 10 秒窗口内连续请求 10 次：

- 1 次受理，4 次因“一人一券”拒绝，5 次 HTTP 429。
- 原始 JMeter 失败率 **50%**（5 / 10），不能抹掉 429 后声称全部成功。
- 全部业务拒绝占 90%；系统异常 0。
- 最终只生成 1 个订单，MySQL / Redis 库存均由 50 降到 49。

## 超时关闭与幂等回补

以 TTL=6 秒、RocketMQ 延迟级别 2（5 秒）启动专门验收阶段，使用券 106。该设定会使延迟消息早于到期时间，验证定时扫描补关。

实际观察：RESERVED → SUCCEEDED/待支付 → SUCCEEDED/已关闭。MySQL 和 Redis 库存都由 20 → 19 → 20；过期支付被拒绝。

把该订单的 CLOSE 消息重新排队并再次实际投递后，库存仍为 20，只存在一条 RELEASE_CANCELLED 事件。证据见 [超时验收](../loadtest/evidence/20261021-timeout.json)。

## 其他验证

- Java：72 项单元/数据库事务测试通过，包括真实 H2 事务回滚、并发唯一约束、支付/关单竞争、恢复补投和时间类型兼容。H2 不等同于 MySQL，真实 MySQL 链路另由上述测试覆盖。
- 前端：15 项 Node 状态测试通过。
- Redis：实际执行 27 项 Lua 检查，覆盖重复预占、库存耗尽、重复释放、活动时间与滑动窗口；源码 SHA256 随证据保存。
- HTTP：登录、请求幂等、异步落单、日期序列化、账号隔离、重复支付、退出 token 失效均通过。
- 浏览器：在实际页面完成商户查询、演示登录、抢券和模拟支付，订单页显示已支付；检查了手机宽度布局。

## 如何复现

按 README 启动依赖、初始化空演示库、构建应用，再按 [脚本说明](../scripts/README.md) 切换缓存模式与运行 JMeter。不能把旧订单和旧用户直接重复用于同一轮库存实验。

原始 JTL 不含 token、请求头、响应正文。公开证据是当时快照；之后超时关单会改变运行中的库存和订单状态。
